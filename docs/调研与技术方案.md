# 递话（Dihua）：微信「转发到其他应用」→ ChatGPT（Codex）桌面端 · 调研与技术方案 v2

- 日期：2026-09-07（v2：改为 Electron 实现；只通过深链投递到 ChatGPT.app；产品名定为「递话」）
- 环境：macOS 15.7.3 · WeChat for Mac 4.1.13 · ChatGPT.app（Codex 桌面端，bundle id `com.openai.codex`，26.901.51231）· Node 22.23.1 / pnpm 10 · `notarytool` 1.0.0（Command Line Tools 自带，无需 Xcode）
- 证据来源：本机 `WeChat.app/Contents/Resources/wechat.dylib` 字符串、`ChatGPT.app` 的 Info.plist 与 `app.asar`、electron-builder 与 Electron 官方源码/文档、公开报道（文末）。

## 0. 一页结论

1. **微信的「转发到其他应用」= 腾讯白名单 App + macOS 系统共享服务列表（2026-09-08 实测修正）。** 微信先把所选消息打成 `聊天记录_<时间>.zip`（内含 `聊天记录.txt` 和媒体）；菜单第一项是服务端下发的「企业微信」，第二项「选择电脑中的应用」子菜单里是 AirDrop / Messages / Notes / Freeform，这与 `NSSharingService.sharingServicesForItems([zip])` 的返回完全一致，即 **系统共享菜单（Share Extension）**，不是 LaunchServices「打开方式」。所以 App 必须内嵌一个 `com.apple.share-services` 类型的 `.appex` 并启用；只登记 zip 文档类型是不够的（那只影响 Finder 的「打开方式」）。
2. **Electron 路线已核实可行**：Electron 主程序 + 一个用 Command Line Tools 的 `clang` 编译的 Objective-C Share Extension（`native/share-extension/`），由 electron-builder 的 `extraFiles` 放进 `Contents/PlugIns/`，ad-hoc 签名时给 appex 单独签沙盒权限；扩展把分享进来的 zip 复制到自己的沙盒临时目录，再用 `dihua://import?path=…` 拉起主程序（`app.on('open-url')`），主程序启动时用 `pluginkit -e use -i app.dihua.desktop.share` 自动启用扩展。投递用 `shell.openExternal('codex://…')`，用 `app.getApplicationInfoForProtocol('codex://')` 探测 ChatGPT.app 并拿图标。全程**不需要 Xcode**。
3. **投递方式只用深链**：`codex://threads/new?path=<已存在目录>&prompt=<文字>`。已在 ChatGPT.app 代码中确认参数白名单为 `originUrl` / `path` / `prompt`，`path` 必须是已存在目录。效果是打开 ChatGPT.app、把目录设为项目并预填提示词，**用户按一次回车发送**（深链不支持自动发送，这是平台限制）。
4. **产品名：递话（Dihua）**。「递」是核心动作——把微信里的话递给任何 AI；不绑定 Codex，后续接 Cursor、Claude、元宝等只是多一个「目标适配器」。scheme `dihua://`，appId `app.dihua.desktop`。
5. **两个必须先验证的假设**（M0）：① 登记了 zip 的第三方 App 确实出现在微信面板里（本机目前只有归档实用工具登记了 zip，所以面板里看不到别的）；② `聊天记录.txt` 的逐行格式（二进制里只找到了文件名与占位符模板）。

## 1. 调研发现

### 1.0 实测修正（2026-09-08）

用户截图显示「转发到其他应用」菜单为：`企业微信` ＋ `选择电脑中的应用 ▸ AirDrop / Messages / Notes / Freeform`。本机执行 `NSSharingService.sharingServicesForItems([zip])` 得到的列表一模一样，说明该子菜单读取的是 **macOS 共享服务**。因此：

- §1.1 里由 `OpenWith*` 字符串推断的「LaunchServices 打开方式列表」**不成立**（那些字符串对应微信内部其他的「打开方式」功能）。
- 第三方 App 进入这个菜单的唯一途径是 **Share Extension**，且第三方扩展默认关闭（`pluginkit -m -p com.apple.share-services` 里 QQ、微信自己的扩展都没有 `+`），需要 `pluginkit -e use -i <id>` 或用户在「系统设置 → 通用 → 登录项与扩展 → 扩展 → 共享」里打开。
- 已实现并验证：内嵌 `DihuaShare.appex` 后，`sharingServicesForItems` 返回 `AirDrop / Messages / Notes / 递话 / Freeform`；用 `NSSharingService.performWithItems:` 驱动该扩展分享样例 zip，主程序成功接收并生成工作区。

**真实导出格式（2026-09-08 实测，微信 Mac 4.1.13）**

- zip 名：`聊天记录_YYYYMMDD_HHMMSS.zip`；条目名 UTF-8（通用标志位 0x0806，含 bit 11）；`unzip` 命令行在 C locale 下会显示乱码但内容正确。
- 内容：根目录 `聊天记录.txt`（UTF-8、无 BOM、LF），媒体在子目录 `聊天记录内的图片、视频和文件/`，图片命名 `微信图片_YYYYMMDDHHmm_N.jpg`。
- TXT 三段块格式，块之间空一行，**没有标题行也没有尾行**：

```
·张航                 ← 发言人，前面带间隔号「·」
2026年9月7日 23:53    ← 中文日期，无秒
等会三点还有个会        ← 正文，可多行
                      ← 空行分隔
```

- 表情写成 `[亲亲]`、`[动画表情]`；图片写成 `[图片] 微信图片_202609080100_1.jpg`（与二进制里的模板一致）。
- 解析器以「发言人行 + 紧随其后的时间行」做块头识别（`parse.ts` 的 `block` 格式），标题由参与者拼成（如「张航、清风明月」）。脱敏 fixture：`fixtures/wechat-4.1.13-聊天记录.txt`；真实样本放 `fixtures/raw/`（gitignore）。

### 1.1 微信侧：转发面板的真实机制（原始推断，部分已被 1.0 修正）

来自 `wechat.dylib`（4.1.13）的字符串：

| 证据 | 说明 |
|---|---|
| `转发到其他应用` / `Forward to Another App` | 菜单项文案 |
| `转发到其他应用时，聊天记录将会被打包成压缩文件进行发送。` | 官方确认打包成 zip |
| `聊天记录_%s.zip`、`聊天记录.txt`；英文 `Chat History_%s.zip`、`Chat History.txt`；繁体 `聊天記錄_%s.zip`、`聊天記錄.txt` | 文件名**随微信界面语言变化**，解析时不能写死 |
| `[图片] 微信图片_%s.jpg`、`[视频] 微信视频_%s.mp4`、`[文件] %s`、`[动画表情]`、`[聊天记录]`、`[语音通话]`、`[视频通话]`、`[视频号名片]`；英文 `[Image] Weixin image_%s.jpg`、`[Video] Weixin video_%s.mp4`、`[File] %s` | TXT 里媒体消息的占位符与媒体文件命名规则 |
| `以上为分享的%d条聊天记录` | 疑似 TXT 尾行，可校验条数 |
| `mmui::OpenWithWindowView`、`OpenWithItemView`、`OpenWithEndItemView`、`openwith_util.cc`、`open_with_other`、`FileOpenWith` | 面板是自绘「打开方式」窗口；`EndItemView` 很可能是末尾的「其他应用…」 |
| `SetupDynamicApps`、`app_meta_info`、`install_path`、`mac_bundle_id`、`以下为腾讯官方出品的其他应用`、`application_yuanbao`、`application_weclaw`、`转发到企业微信` | 腾讯官方 App（企业微信 / 元宝 / ClawBot）由服务端白名单下发，第三方进不了这一区 |
| `_LSCopyApplicationURLsForURL`、`_LSCopyDefaultApplicationURLForURL`、`openURLs:withApplicationAtURL:configuration:completionHandler:`、`NSWorkspaceOpenConfiguration` | 用 LaunchServices 枚举能打开该文件的 App 并调起 |
| `third_app_icon.db`（本机存在，SQLCipher 加密） | 第三方 App 图标缓存 |
| `NSSharingServicePicker` 也存在 | 用于其他分享场景，与转发面板无关 |

本机 LaunchServices 当前登记可打开 zip 的 App 只有 `Archive Utility.app`；ChatGPT.app 只登记了 `public.folder` 与 csv/docx/pptx/xlsx。

推断的面板构成（M0 验证）：

```
┌──────────────────────────────────────────┐
│  以下为腾讯官方出品的其他应用                 │  ← 服务端白名单：企业微信 / 元宝 / ClawBot
│  [企业微信] [元宝] [ClawBot]                │
│  ─────────────────────────────────────── │
│  [归档实用工具] [递话] … [其他应用…]          │  ← LSCopyApplicationURLsForURL(zip) + open_with_other
└──────────────────────────────────────────┘
```

公开报道（腾讯新闻 2026-05-15）印证了用户路径：选中聊天记录 → 转发到其他应用 → 选元宝 → 可补充提示词。微信 4.1.13 官方日志只写了「图片视频可以合并发送」，说明入口早于 4.1.13 存在，4.1.13 起把媒体一并打包。

### 1.2 ChatGPT.app（Codex 桌面端）的接入面

- 本机 Codex 桌面端就是 `/Applications/ChatGPT.app`（bundle id `com.openai.codex`，Codex Framework 152.0.7977.83，Chromium 内核）。`/Applications/Codex.app` 已不存在。
- Info.plist 注册 URL scheme：`codex`、`http`、`https`；文档类型 `public.folder`（Viewer）。
- 深链路由（`app.asar` 中 `/codex/deeplink`，参数白名单 `["originUrl","path","prompt"]`）：
  - `codex://threads/new?path=<绝对目录>&prompt=<文字>`：`path` 必须是**已存在的目录**（代码里 `stat().isDirectory()`），否则回退到 `originUrl` 按 git 远程匹配已有项目；`prompt` 只预填输入框。
  - `codex://threads/<threadId>` 打开既有线程；另有 `codex://review?pr=&path=&line=`、`codex://settings/...`、`codex://plugins/...`、`codex://space`。
- 桌面端线程列表按项目目录（cwd）过滤；用深链 `path` 打开一次，目录就成为项目。
- 深链无法自动发送。要全自动只能走 Codex CLI 的 `app-server` / `exec`（**本期不做**，见附录 A）。

### 1.3 Electron 路线核实

| 需求 | Electron / electron-builder 能力 | 出处 |
|---|---|---|
| 成为 zip 的「打开方式」候选 | `mac.fileAssociations: [{ ext: 'zip', role: 'Viewer', rank: 'Alternate' }]` → `CFBundleDocumentTypes` + `CFBundleTypeRole` + `LSHandlerRank`。`role` 允许 `Editor|Viewer|Shell|None`（默认 Editor），`rank` 允许 `Owner|Default|Alternate|None`（默认 Default） | electron-builder `FileAssociation.ts` |
| 兜底：按 UTType 登记 | `mac.extendInfo` 可注入任意 Info.plist 键，例如 `CFBundleDocumentTypes` 里加 `LSItemContentTypes: [public.zip-archive]`（与 fileAssociations 二选一，避免重复） | electron-builder `macOptions.ts` |
| 接收微信递来的文件 | `app.on('open-file', (e, path) => …)`，**可能在 `ready` 之前触发**，必须在主进程入口最顶部注册并 `event.preventDefault()`，先入队再处理 | Electron `app` 文档 |
| 自动化 URL（`dihua://`） | electron-builder `protocols` + `app.on('open-url')` | 同上 |
| 探测 ChatGPT.app | `app.getApplicationNameForProtocol('codex://')`（空串=未安装）、`app.getApplicationInfoForProtocol('codex://')` → `{ name, path, icon }`，可直接在 UI 里显示目标 App 图标 | 同上 |
| 打开深链 | `shell.openExternal(url)` | 同上 |
| 签名/公证 | hardened runtime 默认开；`notarize` 集成 `@electron/notarize`；本机 `notarytool` 可用 | electron-builder `macOptions.ts`；本机检查 |
| Windows 版 | 微信 Windows 4.1.13 有同样的功能；同一套代码，Windows 用 `process.argv` 取文件路径 | Electron 文档 |

本机：Node 22.23.1、npm 10、pnpm 10、yarn 1.22；`~/Library/Caches/electron` 已有缓存（装过 Electron）。

## 2. 产品定义

### 2.1 名称

**递话（Dihua）**——「把微信里的话，递给任何 AI」。

- 「递」是动作本身（微信 → 递话 → AI），两个字、好读、不绑定任何 AI 厂商；搜索未见同名产品。
- 英文直接用拼音 `Dihua`；appId `app.dihua.desktop`；scheme `dihua://`；工作区根目录 `~/Documents/dihua/`。
- 备选：接力（Relay，英文撞名多）、传送门（Portal，太泛）、Fwd（只有英文）。正式发布前做一次商标/域名检索。

### 2.2 形态

- 平时不驻留。被微信共享菜单调起 → 弹出**投递确认窗** → 用户看一眼预览、选目标、点「递给 ChatGPT」→ ChatGPT.app 打开新线程并预填「记录在哪、是什么」→ 用户在 ChatGPT 里说要求、回车。
- 设置窗（780×560，视觉规范参考 Dukou）：通用 / 入口（共享菜单入口开关）/ 目标应用 / 记录 / 关于。任务模板已去掉（2026-09-08）。
- 同时是 Finder 里任何 zip 的「打开方式」候选；也支持把 zip 拖进主窗口。

### 2.3 UI 技术栈

- Electron 44（Node 22）· electron-vite 5 · electron-builder 26 · React 19 + TypeScript
- **Ant Design 6**（`antd` 6.6.x，已定）+ `@ant-design/icons` 6。**不用 `@ant-design/pro-components`**：其 2.8.10 的 peerDependencies 只声明 `antd ^4 || ^5`，与 antd 6 不兼容；本应用页面简单，`List` / `Form` / `Table` 足够
- 主题：根组件 `ConfigProvider` 统一 `locale`（`zhCN` / `zhTW` / `enUS` 随设置切换）与 `theme`：`algorithm` 跟随系统深浅色（主进程用 `nativeTheme` 监听并广播，渲染进程在 `defaultAlgorithm` / `darkAlgorithm` 间切换），确认窗叠加 `compactAlgorithm`；token 设 `fontFamily: -apple-system, "PingFang SC", …`、`borderRadius: 8`、`colorPrimary` 用递话品牌色，贴近 macOS
- 组件映射：确认窗 = `Descriptions`（会话名/时间范围/条数/媒体数）+ `List` 预览（长记录用 `rc-virtual-list`）+ `Card` 目标卡片（`Avatar` 图标来自 `getApplicationInfoForProtocol`）+ `Segmented` 模板 + `Input.TextArea` 附加说明 + `Checkbox` 下次不再询问 + 主按钮「递给 ChatGPT」；主窗口 = `Layout.Sider` + `Menu` 左侧栏，收件箱 `List`（`Card` 项 + `Dropdown` 操作），目标应用 `Card` 网格 + `Badge` 探测状态，模板与设置用 `Form`（`Form.List` 管理多模板）；反馈用 `Result` / `notification` / `Progress`
- 窗口：`titleBarStyle: 'hiddenInset'`，自绘顶部拖拽区（`-webkit-app-region: drag`）；不开 `vibrancy`（antd 的 `colorBgLayout` 与透明背景不搭）；确认窗 680×560 独立 `BrowserWindow`
- zustand（渲染进程状态）· react-i18next（业务文案；antd `locale` 只覆盖组件内置文案）

## 3. 技术架构

### 3.1 数据流

```
微信 4.1.13                          递话（Electron）                                   ChatGPT.app
多选 → 转发 → 转发到其他应用           main 进程                                           （Codex 桌面端）
   │ 打包 聊天记录_<时间>.zip           ┌────────────────────────────────────────┐
   └─(LaunchServices 打开方式)────────→│ open-file → intake  复制到 userData/incoming │
                                      │ extract  yauzl 流式解压，文件名 UTF-8→GB18030 │
                                      │ parse    TXT → Transcript（占位符关联媒体）  │
                                      │ workspace ~/Documents/dihua/inbox/<id>/        │
                                      │ targets  codex 适配器 → 深链                  │──shell.openExternal──→ codex://threads/new?path=…&prompt=…
                                      └───────────┬────────────────────────────┘                          打开项目 + 预填提示词 → 用户回车
                                                  │ IPC（contextBridge）
                                      renderer：投递确认窗 / 收件箱 / 目标 / 模板 / 设置
```

### 3.3 主进程模块

| 模块 | 职责 | 关键点 |
|---|---|---|
| `index.ts` | 生命周期 | `requestSingleInstanceLock()`；`open-file`/`open-url` 在文件顶部注册，`ready` 前入队，`ready` 后逐个处理 |
| `intake.ts` | 接收 | 微信容器里的 zip 转发后可能被清理，**收到路径立即复制**到 `userData/incoming/<uuid>.zip`；校验 `PK\x03\x04` 魔数与大小上限（默认 2 GB） |
| `extract.ts` | 解压 | `yauzl`（`decodeStrings: false` 拿原始字节）+ `iconv-lite`：通用标志位 bit 11 为 UTF-8 则直接解码，否则 UTF-8 校验失败回退 GB18030；拒绝 `..` 路径；流式写盘（视频可能很大） |
| `parse.ts` | TXT → 消息 | 定位：按语言候选名（`聊天记录.txt` / `聊天記錄.txt` / `Chat History.txt`）→ 兜底「唯一的 .txt」。两套行头正则投票（时间在前 / 人名在前），正文到下一行头为止；占位符 `[图片] 微信图片_x.jpg` 关联 `媒体/` 下同名文件；尾行校验条数；命中率 < 60% 置信度 `low`，原文透传 |
| `workspace.ts` | 生成工作区 | 固定根目录 `~/Documents/dihua/`（一次成为 ChatGPT.app 项目，后续线程都归它）；每次 `inbox/<yyyyMMdd-HHmmss>-<会话名>/`；`transcript.md`、`meta.json`、`prompt.md`、`原始/`、`媒体/`；根目录 `AGENTS.md`（Codex 启动自动读）；视频缩略图 v1 用系统 `qlmanage -t -s 1024`（零依赖），后续可换 `ffmpeg-static` 抽多帧 |
| `targets/` | 投递适配器 | 接口 `Target { id, name, capabilities, detect(), deliver(job) }`；`codex.ts` 见 §5.3；注册表决定确认窗里的目标卡片与默认目标 |
| `handoff.ts` | 递交上下文 | 只预填「记录在哪、是什么」（相对路径、会话名、条数、时间范围、媒体概况），结尾留给用户写要求；**不再有任务模板**（2026-09-08 用户决定） |
| `store.ts` | 持久化 | `electron-store`：根目录、默认目标、默认模板、是否跳过确认、保留天数、语言；历史索引 JSON |

### 5.2 主进程入口（open-file 必须最早注册）

```ts
// src/main/index.ts
import { app, shell } from 'electron'
import { intake } from './intake'
import { automation } from './automation'

const pendingFiles: string[] = []
const pendingUrls: string[] = []

app.on('open-file', (event, filePath) => {          // 微信「打开方式」调起时触发，可能早于 ready
  event.preventDefault()
  app.isReady() ? void intake.handle(filePath) : pendingFiles.push(filePath)
})
app.on('open-url', (event, url) => {                 // dihua:// 自动化
  event.preventDefault()
  app.isReady() ? void automation.handle(url) : pendingUrls.push(url)
})

if (!app.requestSingleInstanceLock()) app.quit()

app.whenReady().then(async () => {
  for (const p of pendingFiles.splice(0)) await intake.handle(p)
  for (const u of pendingUrls.splice(0)) await automation.handle(u)
  if (process.argv[1]?.endsWith('.zip')) await intake.handle(process.argv[1])   // 开发模式 / Windows
})
```

### 5.3 目标适配器与 Codex 深链

```ts
// src/main/targets/types.ts
export interface Target {
  id: string
  name: string
  capabilities: { autoSend: boolean; attachments: 'workspace' | 'inline' | 'none' }
  detect(): Promise<{ available: boolean; appName?: string; appPath?: string; icon?: string }>
  deliver(job: DeliveryJob): Promise<void>
}

// src/main/targets/codex.ts
import { app, shell } from 'electron'
export const codexTarget: Target = {
  id: 'codex',
  name: 'ChatGPT（Codex）',
  capabilities: { autoSend: false, attachments: 'workspace' },
  async detect() {
    const name = app.getApplicationNameForProtocol('codex://')
    if (!name) return { available: false }
    const info = await app.getApplicationInfoForProtocol('codex://')
    return { available: true, appName: info.name, appPath: info.path, icon: info.icon.toDataURL() }
  },
  async deliver(job) {
    const url = new URL('codex://threads/new')
    url.searchParams.set('path', job.workspaceRoot)      // 必须是已存在的绝对目录
    url.searchParams.set('prompt', job.prompt)           // 只预填，用户回车发送
    await shell.openExternal(url.toString())
  },
}
```

### 5.7 Gemini 桌面端适配器（2026-09-09 实测，Gemini.app 1.107.3 / 1.111.1）

**能不能走深链：不能。**

- `/Applications/Gemini.app`（`com.google.GeminiMacOS`，要求 macOS 15）的 Info.plist 没有 `CFBundleURLTypes`；`lsregister -dump` 里也没有任何 gemini 开头的 scheme 绑定。
- 二进制里有 `geminimacos://action/scheduleEditor/askGemini` 这类 URL 和 `appDeeplinkURLScheme`，但没登记到 LaunchServices，只能在应用内部用；`open geminimacos://…` 会报没有应用能打开。
- 签名 entitlements 里没有 `associated-domains`，所以 `https://gemini.google.com/…` 不会以 universal link 的方式落进桌面端。
- 没有 `Metadata.appintents`（无 Shortcuts 动作）、没有 `.sdef`（无 AppleScript 词典）、没有 `NSServices`。`NSUserActivityTypes` 只有 `com.google.gemini.handoff`（iOS/macOS 接力）。
- 应用有 `network.server` 权限和 `http://localhost:2444/submit`，那是 OAuth 回调，不是本地 API。

**能走什么：文件。**

- 文档类型登记了 `public.item`（所有文件，Viewer，rank None），并实现了 `application:openFiles:`。`open -a Gemini a.md b.jpg` 会把文件作为附件放进**当前**输入框（New chat 或正打开的会话），同时弹出一个「Gemini Mini Chat」浮窗；`.md` 显示为文档图标，图片显示缩略图；目录被忽略。
- **冷启动时随 `open` 一起送的文件会丢**（界面还没好）。实测进程出现后 2 s 再送就能接住；适配器用「`open -a Gemini` → 轮询 `pgrep` → 等 3.5 s → `open -a Gemini <文件…>`」。
- 提示词没有任何预填途径，只能进剪贴板，用户 ⌘V。

**适配器行为（`src/main/targets/gemini.ts`）**

```
detect  : /Applications/Gemini.app 或 ~/Applications/Gemini.app，否则 mdfind kMDItemCFBundleIdentifier；不取系统图标（见下）
deliver : clipboard.writeText(prompt)
          → 未运行则拉起并等就绪
          → open -a Gemini transcript.md [图片…] [文档…] [视频…]   （最多 10 个，见 targets/attachments.ts）
```

附件顺序：transcript.md 先占一个名额，剩下按 图片 → 文档（文件/ 下的 pdf/docx/xlsx/txt…）→ 视频 填满，单个超过 100 MB 的跳过。提示词（`handoff.ts` 的附件模式）会写明附件里有什么、有几个没带上：

```
我从微信递来一份聊天记录，就是附件里的 transcript.md（项目群，20 条，2026-09-07 23:53 至 2026-09-08 01:00）。
附件里还有 9 张图片。另有 3 张图片、1 段视频受附件数量限制没带上，需要的话我再补。请先通读它，然后按我下面的要求处理：
```

坑：`app.getFileIcon('/Applications/Gemini.app', { size: 'large' })` 会让 Electron 44 主进程在 ThreadPoolForegroundWorker 上 EXC_BREAKPOINT 崩溃（隔离脚本可复现；`size: 'normal'` 不崩但只有 32px），所以 Gemini 的图标用界面里的品牌 SVG，不走系统图标。

已知限制：附件落在 Gemini 当前打开的输入框里，用户若正停在旧会话上，附件就进了旧会话；`.md` 在输入框里显示为文档，若某个版本拒收，把 transcript 另存 `.txt` 再送即可（`attachments.ts` 改一处）。

### 5.8 Claude 桌面端适配器（2026-09-09 源码分析 + 实测，Claude.app 1.28929 → 1.46388）

**能走深链。** `/Applications/Claude.app`（`com.anthropic.claudefordesktop`，Electron）登记了 `claude://`；主进程 `claudeURLHandler` 按 host 路由（`app.asar/.vite/build/index.chunk-*.js`，用项目里的 `@electron/asar` 解包即可读）：

| 深链 | 进到哪 | 说明 |
|---|---|---|
| `claude://cowork/new?q=<文字>` | `/task/new?q=`，Cowork 新任务 | **递话用这条（只带 q）。** `q` 截到 14336 字符（`1024*16-2*1024`） |
| `claude://cowork/new?q=&folder=<目录>[&file=<文件>]` | `/task/new?q&folder&file&src=external` | 目录/文件挂到任务上，但 `src=external` 会让网页弹「Another app wants Claude to work in “<目录名>”」/「wants to attach “<文件名>”」授权框；**点允许后页面重载，q 丢失**（已信任的目录也照样弹「You've allowed this folder before. Continue…」）。所以不用 |
| `claude://claude.ai/new?q=<文字>[&surface=chat]` | claude.ai 普通对话 `/new?q=` | 只预填文字，带不了本地文件 |
| `claude://code/new?q=<文字>&folder=<目录>` | Claude Code 会话 | 写代码的场景 |
| `claude://claude.ai/chat/<uuid>` / `project/<uuid>` | 打开既有对话 / 项目 | 没有创建项目或往项目知识里传文件的深链 |

**目录怎么挂而不弹框：走系统「打开方式」。** Claude.app 的文档类型登记了 `public.folder`（Editor）和 `public.data`；`open -a Claude <目录>` 触发 `app.on('open-file')` → `Handling folder drop` → `dispatchOnCoworkFromMain({selectedDirectories})`，这是「把目录拖到 Dock 图标」的路径，网页把它当用户自己的操作：已信任的目录直接 `setDraftSessionFolders: 1 folders`，输入框下出现目录 chip，不弹框（首次遇到的目录会问一次是否信任）。草稿任务的目录存在主进程内存里（`draftSessionFolders`），随后导航到 `/task/new?q=` 时仍然带着。信任列表存在 `~/Library/Application Support/Claude/claude_desktop_config.json` 的 `preferences.localAgentModeTrustedFolders`，父目录被信任则子目录也算信任。

**适配器行为（`src/main/targets/claude.ts`，能力 `attachments: 'workspace'`）**

```
detect  : app.getApplicationInfoForProtocol('claude://') 且路径以 Claude.app 结尾；否则看 /Applications/Claude.app
deliver : 未运行则 open -a Claude，pgrep 到进程后等 6 s（主视图要载入 claude.ai）
          → open -a Claude <工作区根目录>        （目录挂到 Cowork 草稿任务）
          → 等 2 s
          → shell.openExternal('claude://cowork/new?q=<提示词>')
```

提示词与 ChatGPT 共用「工作区」措辞（`handoff.ts` 不传 plan）：目录是整个工作区，提示词里说清 `inbox/<时间>-<会话名>/transcript.md`。Cowork 能读目录里的图片。

冷启动时：open-file 与 open-url 都会被 Claude 排队到主视图就绪后处理，目录先于深链登记，顺序有保障；适配器仍先拉起并等 6 s，避免两者挤在一起。

### 5.9 共享菜单里的「递给 X」直达入口（2026-09-10）

需求：开了「收到记录后直接递出去」后，微信「转发到其他应用 → 选择电脑中的应用」里直接列出目标应用，点哪个就递给哪个。

做法：同一份 Share Extension 代码打成多个 appex（`scripts/build-share-extension.sh`）：

| appex | bundle id | 显示名 | Info.plist 额外键 |
|---|---|---|---|
| DihuaShare.appex | app.dihua.desktop.share | 递话 | — |
| DihuaShare-codex.appex | app.dihua.desktop.share.codex | 递给 ChatGPT | DihuaTarget=codex |
| DihuaShare-claude.appex | app.dihua.desktop.share.claude | 递给 Claude | DihuaTarget=claude |
| DihuaShare-gemini.appex | app.dihua.desktop.share.gemini | 递给 Gemini | DihuaTarget=gemini |

- 扩展启动时读自己 Info.plist 的 `DihuaTarget`，附在 `dihua://import?path=…&source=share&target=<id>` 上；主进程 `handleIncomingFile(path, source, targetId)` 有 targetId 就直接 `deliverJob`，目标不可用时通知一声并退回确认窗。
- 图标：`native/share-extension/icons/<target>.svg`（白底圆角方块 + 品牌 logo），构建时 `qlmanage -t -s 1024` 渲染成 PNG → `sips` 缩各档 → `iconutil -c icns`，写进 appex 的 `CFBundleIconFile`；任一步失败就不带图标，回退到主程序图标。通用「递话」入口仍用主程序图标。
- 开关同步（`entries.ts` `syncShareEntries`）：`pluginkit -e use/ignore -i <id>`。规则：「入口」关 → 全关；`skipConfirm` 且有已开启且已安装的目标 → 只开这些目标的入口，通用入口关；否则只开通用入口。启动时、`settings:set` 改到 skipConfirm/defaultTargetId/disabledTargetIds 时、`targets:setEnabled` 时都会同步。`pluginkit -m -i` 匹配时带上「(」，避免 `.share` 匹配到 `.share.codex`。
- 各扩展的沙盒容器是 `~/Library/Containers/app.dihua.desktop.share[.<target>]/Data/tmp`，主进程按前缀判断「复制完就删源文件」。
- 显示名在 appex 的 Info.plist 里是构建期写死的，`Target.shareLabel` 必须与之一致（「入口」页显示用）。

### 5.10 更新检查与发布（2026-09-10）

- 递话是 ad-hoc 签名的开源应用，Squirrel.Mac 不接受未经 Developer ID 签名的自动替换，所以不用 electron-updater，只做「检查 + 提示 + 下载链接」。
- `src/main/update.ts`：`net.fetch` GitHub `/repos/<owner>/<repo>/releases/latest`（10 s 超时；404 = 还没发布过），`updateCheck.ts` 里的纯函数比版本号（前导 v、预发布后缀）、按 `process.arch` 挑 `Dihua-<version>-<arch>.dmg`。结果缓存在 `userData/update.json`，`update:changed` 广播给各窗口。
- 自动检查：打包版启动 15 s 后、距上次检查超过 24 h 才查；有新版本且不是「跳过的版本」就弹系统通知，点击打开下载链接。设置项 `autoCheckUpdates` / `skippedUpdateVersion`。
- 关于页「更新」卡：当前版本、状态、检查更新、下载、跳过这个版本、更新说明（Release body）、自动检查开关、所有版本链接。
- 仓库名只在 `src/shared/repo.ts` 与 `package.json` 两处。
- 发布：`.github/workflows/release.yml` 在推 `v*` 标签时跑（标签须等于 `v${package.json.version}`），macOS runner 上编共享扩展（clang / qlmanage / iconutil 都有）、`electron-builder --mac dmg zip --arm64 --x64`，`scripts/after-pack.cjs` 做 ad-hoc 签名，`softprops/action-gh-release` 上传 dmg/zip 并自动生成说明。`ci.yml` 在 push / PR 时跑 typecheck、单测、扩展编译。
- 清理（为开源）：删掉了 0.0.1 前中文目录迁移（migrate.ts）、无人引用的 antd 薄封装（components/ui.tsx）、没有目标在用的「正文进提示词」模式（handoff.ts 的 text 模式与对应测试）、未被引用的 build/icon.png；`build/share-extension/` 与 `fixtures/raw/` 进 .gitignore；补 LICENSE（MIT）、.gitattributes、package.json 的 repository/homepage/bugs/engines。

## 附录 A · 暂不做的全自动路径（Codex CLI）

本期只用深链。若以后要「不按回车也自动开始分析」，Codex CLI 0.153.4 提供两条路径，主进程用 `child_process` 即可接：

- `codex app-server`（stdio JSON-RPC）：`initialize` → `thread/start {cwd, sandbox:"read-only", approvalPolicy:"never"}` → `turn/start {threadId, input:[{type:"text"},{type:"localImage",path}]}`，通知 `item/agentMessage/delta`、`turn/completed`。
